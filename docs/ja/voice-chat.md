# 無線での音声

SimPitRadio は、あなたが言ったことをゲームのチャット欄に入力します。ここで加わるの
はもう半分です。一緒に走っている人たちが*音声*も送ってきて、あなたはそれを聞きます。

これは意図的に Discord ではありません。Discord はすでに存在し、ちゃんと動き、みん
なすでにどこかに入っています。Discord にできないのは、事前の段取りなしに **今この
セッションにいる人** と同じ部屋にあなたを入れ、4 キロ先にいる人を黙らせることです。

## 何が流れるのか

**プッシュトゥトークのクリップが、指を離した時点で。ライブストリームではありませ
ん。**

トリガーの処理は、キーが押されているあいだすでにクリップを録音し、離した時点でそ
れを Whisper に渡しています。ボイスはそのまったく同じクリップを再利用します。離し
た時点で、Whisper *と* リレーの両方へ送られ、相手側がそれを再生します。録音の経路
は何も変わりません。

ライブストリームは別のアプリケーションになります。20ms のフレーミング、ジッタバッ
ファ、ミキサー、再生クロックが必要で、しかもすべて音声処理の経路上に置かれ、その
見返りは相手が 1.5 秒早く聞けることです。クリップというのは、そもそもピット無線そ
のものです。ボタンを押し、何かを言い、それが届く。

知っておく価値のある帰結。**クリップは不可分です。** 途中で割り込むことはできず、
まるごと届くか、まったく届かないかのどちらかで、2 人が同時に話せば 2 つのクリップ
ができ、重なるのではなく順番に並びます。これは無線が重なるより悪いのではなく、良
いことです。

## 誰に聞こえるのか

リレーは何も考えません。部屋にいる全員へクリップをそのまま配り、誰が受け取るべき
かの判断はしません。できないからです — 誰がコースのどこにいるかを知りませんし、そ
の情報を渡すことは、役に立たないどころか害になります。

**近さは聞き手のマシンで決められます。** LMU の共有メモリは、あなたのだけでなく
*すべての*車のワールド座標を持っているので、各クライアントはすでに、他のドライバー
全員がどれだけ離れているかを正確に知っています。位置に関するものがリレーへ公開さ
れることは一度もなく、この機能はリレーの運用者が悪意を持っていても働きます。

**話し手がどこにいるかは、聞き手自身の見え方が優先されます。** クリップは話し手が
話し終えた後に届くので、そこに載っている位置は 1、2 秒古いものです — レース速度で
は 100 メートル、半径 200m に対しては答えを左右する差です。スコアリングのブロック
には*今この瞬間*の全車がいますし、問うべきは、メッセージが再生される時点で対象の
車の近くにいるのは誰か、です。

それでもクリップは話し手の位置を運びます。聞き手側のブロックがまだ追いついていな
い相手 — 参加したばかりのドライバーや、エントリーが消えたドライバー — のための代替
としてです。古い位置は、無いよりましです。

手元の見え方を優先するということは、クリップが自己申告でフィルタを通り抜けられな
いということでもあります。1 キロ離れているのに真横にいると称するクライアントは、実
際にいる場所で測られるだけです。これはセキュリティの仕組みではなく、新しいほうの
数字を使うことの帰結です — まったく位置を特定できない話し手の声は、それでも聞こえ
ます。理由の説明できない無音のほうが、悪い失敗だからです。

LMU プラグインの `proximity_only` がこれを有効にし、`proximity_metres` が半径を決
めます。切れば、セッション全体が聞こえます。練習走行やフォーメーションラップでは、
そちらが望ましい状態です。

### 観戦中

近さは、画面に映っている車から測られるべきです。自分がその只中にいるバトルを見な
がら、自分の車が停めてある 4 キロ先の無線を聞くのは、見ている人の感覚でいう「近
さ」ではありません。

これは **検出される** 必要があります。走っている人はドロップダウンに手を伸ばせませ
んし、観戦している人もそうする必要はないはずです。

**共有メモリのブロックはそれを教えてくれません。** もっともらしい情報源を 3 つ、実
際に観戦中のセッションで確かめて除外しました。どれも正しそうに見えて、どれも違い
ます。

- `telemetry.playerVehicleIdx` は*プレイヤーの*車です。他人を観戦しているあいだも、
  観戦者自身の停まった車を指したままでした。
- `appInfo.mOptionsLocation` は最初から最後まで 0 でした。
- `$rFactor2SMMP_Graphics$` は公開されており、カメラ位置と見ているスロット ID の両
  方を運ぶはずのものです — が、LMU はそこを一度も埋めません。バッファはバージョン
  カウンタを除いて完全にゼロです。rF2 プラグインがそこを埋める元にしているグラフィ
  ックスのコールバックを、ゲームが呼ばないからです。隣の Extended ブロックは同じ瞬
  間に生きていたので、これはインストールの破損ではなく LMU の選択です。

**LMU 自身の HTTP API は教えてくれます。** `http://127.0.0.1:6397/rest/watch/standings`
はゲーム自身のオーバーレイが読んでいるもので、各エントリーが `hasFocus` を持ってい
ます — 観戦されている車に立ち、自分の車に立ったままの `player` とは別物です。その
`slotID` は共有メモリの `mID` と同じ番号なので、二つはそのまま突き合わせられます。
プラグインではなくゲームの一部なので、何もインストールする必要がありません。

短いタイムアウトで読み、1 秒間キャッシュします。これはトリガーの処理上で動きます
し、応答は約 16KB ありますし、読み上げアプリがロード中のゲームを待つことは決してあ
ってはなりません。**失敗もキャッシュされます** — そうしないと、閉じているゲームの
ために押すたびタイムアウトを払うことになります。

失敗はすべて None を返し、`SessionInfo.listener()` はそこから運転中の車へ、最後に
は None へと後退します。`audible` はそれを「聞こえる」と解釈します。黙って停まった
車を基準にし続ければ、誰も見ていない場所を基準にセッションを絞ることになりますし、
聞き手にはそれと壊れた機能との区別がつきません。

**「近さ」とはコース上のことであり、それ以外の何物でもありません。** ゲームの中の
2 台のあいだのメートル数であり、シムから読み、手元で計算されます。誰がどこに住んで
いるかとは無関係で、現実の位置情報を読むことも、導くことも、送ることもありません。
下のリレーの*ホスティング*も距離の話をしますが、あれはネットワーク上の意味であり、
サーバーの経路の話で、誰の声が聞こえるかとは無関係です。

## どの部屋か

セッション ID は導出されるもので、公表されることはありません。

    sha256("pitradio/1:{mServerPublicIP}:{mServerPort}")[:32]

同じゲームサーバーにいる全員が、それがどのサーバーなのかを誰も公開しないまま同じ
ID を計算します — リレーが知るのはハッシュだけで、ほかには何もありません。オフライ
ンとシングルプレイヤーにはサーバーが無いので、ID も部屋も生まれません。これは特別
扱いではなく、正しい動作です。

コース名はわざと鍵に入れていません。同じサーバーでもセッションごとに変わりますし、
イベントが次のコースへ移った瞬間に消える部屋は、より悪い部屋です。

部屋の中での身元は、スコアリングブロックのドライバー名です。`mSteamID` は実際には
ゼロなので、これ以上のものがありません。

## リレー

**リレーのコードと設定はこのリポジトリにありません。** SimPitRadio は公開されていま
すが、サーバーとその Terraform、Ansible は、それらが必要とする OAuth のクライアン
トシークレットとともに非公開です。あちらの Terraform と Ansible は一つの仕事のため
にあります。**レーサーが提供する**ボイスホストを、まっさらなイメージから再現可能に
立ち上げることです。

基準となるリレーのアドレスも、このリポジトリにはありません。**ビルド時に**
[endpoints.py](../src/pitradio/endpoints.py) へ書き込まれるので、チェックアウト
— あるいはフォーク — にはアドレスがまったく無く、ボイスは単に使えません。これは壊
れた状態ではなく、正しく動いている状態です。ソースの複製すべてが、運ぶことに同意
した覚えのない持ち主のサーバーへマイクを向けているよりは、ずっとましです。

アプリのほかのどこも、アドレスを直接埋め込んではいけません。上書きする場所が一か
所、おかしいときに見る場所も一か所。

    wss://<relay>/chat/{session-id}

クライアントごとに 1 本の WebSocket、TLS、小さなヘッダー付きのバイナリフレームとし
てのクリップ。プロトコルはこれで全部です。TLS なのは、リレーが他人のマシンであり、
あなたの声の録音がそこを平文で渡るべきではないからです。WebSocket なのは、生の UDP
が越えられないあらゆる NAT と企業ファイアウォールを越えられるからであり、ときどき
ボタンを押す 20 人ぶんの音声帯域など無いに等しいからです。

**文字どおりのピアツーピアではありません。** 本当の P2P には ICE と STUN、そして
TURN による代替経路が要ります — そして TURN はリレーですから、代替経路は結局この設
計であり、しかもすでにネイティブ依存と格闘しているビルドへ WebRTC のスタックを引き
込んだ末にそこへ辿り着きます。リレーは小さな箱 1 つで、小さな箱であることを隠しま
せん。

### コミュニティのホスト

リレーは*話している人の近くにいる*ために存在します。3 大陸から集まったグリッドがフ
ランクフルトの 1 台を経由すれば、クリップごとに大西洋を 2 回渡ることになります。そ
の集団のために選ばれたリレーなら、そうはなりません。レーサーがホストできる理由は
そこにあります。費用でもなければ、分散それ自体が目的でもありません — 地理です。

Terraform がマシンを作り、Ansible がリレーと systemd ユニットと TLS 証明書を入れる
ので、ホストはまっさらな Ubuntu イメージから手作業なしで再現できます。

まず DigitalOcean の OAuth です。今あるのがそれだからです。Linode にもまともな
OAuth アプリのフローがあるので続けられます。**AWS はできません**。プロビジョニング
のためのコンシューマ向け OAuth が無く、IAM キーか Identity Center の SSO しかないの
で、独自の経路が必要であり、ボタンを 1 つ足せば済む話ではありません。

#### どれを選ぶかは個人ではなく集団の決定です

**セッション内のすべてのクライアントが同じリレーを選ぶ必要があります。さもなければ
誰も選べません。** 放っておけば各自が*自分に*いちばん近いホストを選ぶので、大西洋
をまたぐグリッドではリレーが 2 つ、部屋が 2 つになり、セッションの両半分がそれぞれ、
機能しているようにしか見えないのに他に誰もいない場所に座ることになります。これは
セッション鍵が食い違ったときと同じ静かな失敗に、別の道から辿り着いたものです。

そこで、固定された基準ホストに調整役が 1 つあり、それが決めます。

1. クライアントはビルドに設定されたリレーで部屋に入り、候補となる各リレーへの往復
   時間の実測値を報告します。
2. 調整役は、部屋全体で最悪値が最も良いものを選びます — 平均ではなく*いちばん遅い*
   レーサーの遅延を最小にします。誰も取り残さないことが目的だからです。
3. 全員に移動を伝え、みなでそちらに繋ぎ直します。

基準ホストは代替のリレーでもあります。それがこの仕組みを安く保っています。調整役
はどのみち常時動いていなければならないので、移すほどでもない小さすぎるセッション
や近すぎるセッションの音声は、ついでに運べばよいのです。

#### なぜホスト同士を橋渡ししないのか

分かりやすい代案があります。各クライアントを*自分の*いちばん近いリレーに繋がせ、リ
レー同士でクリップを転送させる。これは実在する設計ですし — Mumble はこのやり方でサ
ーバーを繋ぎます — 一点において本当により優雅です。上の集団的決定を消せるからです。
部屋がすべてのリレーにまたがるなら、合意すべきことは何もなく、部屋が割れる失敗は
そもそも起こり得ません。

それでもここでは間違った取引です。理由は一つ。**私たちが送るのはクリップであって、
ライブストリームではない** からです。クリップは話し手が話し終えてから送り出される
ので、経路が 90ms か 250ms かの違いは誰にも知覚できません — そしてそれこそが、地理
にこだわる理由のほとんどであり、それを改善するために余分に 2 ホップ払う理由のすべ
てです。

橋渡しが要求するのはホップ数ではなく、状態です。リレーは部屋の在籍を互いに伝え合
い、互いを認証し、ループと二重配送を防がなければなりませんし、その網に加わったレー
サー提供のリレーは、自分のところに誰もいない部屋の通信まで見えてしまいます。それ
は、この設計が抱えてもいない遅延の予算のために、読み上げアプリの脇へ分散システム
のプロジェクトを括りつける行為です。

SimPitRadio がいつかライブストリーミングに移るなら、これは逆転し、橋渡しが正解にな
ります。そのとき作るべき形はこうです。共有秘密を持つフルメッシュ、部屋の在籍の伝
播、そして各クリップが ID を持ち、リレー間は **1 ホップ** まで — 推移的な転送はな
し。これで経路のループは根本から消え、配り先の広がりは信用ではなく上限で抑えられ
ます。

#### ホストが消えたとき

リレーが消えても会話は終わってはいけません。調整役が部屋を保持しており、リレーが
応答しなくなったことに気づき、残ったものの中で選び直し、残っているレーサーを移動さ
せます — 最初に選ぶときとまったく同じ仕組みなので、間違えるための別のフェイルオー
バー経路が存在しません。クライアントが調整役との接続を開いたままにしているのは、ま
さにこのためです。それが生き残るものだからです。

レーサーがセッションを抜けても、レース中に自分のリレーを持ち去ることはありません。
リレーは彼らのマシンではなく、彼らが立てたインスタンスですし、まだ走っている人た
ちの足元からそれを引き抜くのは、考えうる最悪のタイミングです。

#### セッションが終わったとき

部屋は放置されず、畳まれます。LMU はゲームのフェーズを報告するので、セッションの終
了を見たクライアントがそう伝えます。最後のクライアントが去るか、部屋がアイドルの
時間切れまで静かなままなら、調整役がそれを閉じます。部屋が一つも残っていないリレー
は `terraform destroy` の候補です。それが、これがレーサーにとって 1 イベント数十円
で済むか、インスタンスを永久に抱えるかの分かれ目です。

アイドルの時間切れは、明示的な合図と同じくらい重要です。クラッシュしたクライアン
ト、アルトタブしたまま消えたクライアント、ネットワークを失ったクライアントは、何
も送ってきません — ですから、送ってくることに何かを頼らせてはいけません。

## 同意

ボイスはプロファイルごとに **入れるまで切れて** います。そしてウィンドウは、ほかの
何を言うより先に、誰にあなたの声が聞こえるのかを表示します。読み上げアプリが黙っ
て 20 人の見知らぬ人へマイクを開いたなら、それは機能がどれだけ優れていようと裏切り
です。

プッシュトゥトークのみです。オープンマイクのモードは無く、あるべきでもありません。
キーこそが同意だからです。
