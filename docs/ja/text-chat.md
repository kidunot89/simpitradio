# テキストチャット

SimPitRadio がそもそも作られた目的です。トリガーを押したまま言いたいことを言い、
指を離すだけ。両手をハンドルに置いたまま、ゲームのチャット欄へ文字になって現れます。

アプリのほかのものはすべて、ここから育ちました。エンジニアもコーチもボイスチャッ
トも、同じトリガーと同じクリップを共有しています。テキストチャットとは、その言葉
をほかの誰も引き取らなかったときに起きることです。

## キーを押しているあいだに起きること

1. **キーは飲み込まれます。** ゲームはトリガー自体を見ないので、ゲームが使っている
   キーを割り当てても構いません。
2. **録音はすぐに始まります** — チャット欄を開いた後ではなく、開く前に。チャット欄
   が開くには数百ミリ秒かかり、そのあいだに話した内容は、そうでなければ失われてし
   まいます。
3. **チャットキーが送られ**、ゲームのチャット欄が開きます。アプリはそれがフォーカ
   スを得るまで `pre_delay_ms` だけ待ちます。
4. **指を離します。** 録音が止まり、クリップは Whisper に渡されます。動くのはあな
   た自身の CPU です。
5. **テキストが入力され**、続いて送信キーが送られます。

その言葉がエンジニアやコーチへの命令だと分かった場合は、代わりにそちらが答え、何
も入力されません。この判定はわざと狭くしてあります。同じトリガーがセッションの全
員にメッセージを送るので、アプリが勝手に命令だと思い込むことは、黙って届かないメ
ッセージを生むことだからです。参照:
[話しかける](engineer.md#話しかける)。

## 止める

**テキストチャット → ゲームへ送信** は、セッションが公開のものに変わったとき、レー
スの最中に手を伸ばすスイッチです。切ると、トリガーはボイスとエンジニアのためだけ
のものになります。チャットキーもなし、入力もなし、送信もなし。

ゲームごとの二つめのスイッチが、プロファイルの下にあります。「このゲームにチャッ
ト欄はあるか」は、毎回のセッションで決めることではなく、そのゲームについての事実
です — Assetto Corsa のオフラインには開くチャットがないので、押すたびに別の意味を
持つ Enter がゲームへ送られていました。こちらは一度設定したら忘れてかまいません。
アプリ全体のスイッチのほうが常に優先されます。あちらが切なら、どこでも切です。

## 送る前にメッセージを確かめる

既定では、入力され次第すぐに送信されます。音声モデルは聞き間違えますし、公開セッ
ションでの間違いは全員の問題になります。そこで、プロファイルごとに **自動送信** の
切り替えがあります。

これを切ると、メッセージはチャット欄に入力されたまま置かれます。その後どうするか
は、ハンドルから手を離さずに、トリガーで決められます。

| 操作 | 何が起きるか |
| --- | --- |
| **1 回押す** | 送信する |
| **2 回押す** | 消す |
| **長押し** | 消して録り直す |

メッセージが置かれているあいだ、ステータスタブには **送信待ち** と表示されます。

ボタンに余裕があれば、**設定 → トリガー** で *待機中のメッセージを送信* と *待機中
のメッセージを消去* にキーを直接割り当てることもできます。こちらは 2 回押しの待ち
時間なしで即座に働き、上の操作を置き換えるのではなく併存します。

**1 回押しはすぐには実行できません。** 2 回押しの判定時間が閉じるまで、それが 2 回
押しの前半である可能性が残るからです。この待ち時間が `review.double_tap_ms` で、お
よそ 3 分の 1 秒です。設定で `0` にすれば即座に送られますが、2 回押しで消す操作は
使えなくなります。1 回押しと長押しの境目は `review.tap_ms` です。

**メッセージが待機しているあいだの押下は、ただちに録音を始めます。** それが 1 回押
しなのか長押しなのか分かる前に、です。判明するまで待てば録り直しの最初の言葉を飲
み込んでしまいますし、1 回押しだと分かればバッファは捨てられます。

## プロファイル

どのプロファイルが使われるかは、フォーカスを持っている実行ファイルで決まります。
複数のシムを同時に設定しておけば、尋ねられることなく正しいものが使われます。

いちばん重要な設定は **チャットを開く待ち時間**（`pre_delay_ms`）です。チャット欄
が開いてフォーカスを得るには数フレームかかり、早く入力しすぎると冒頭の文字が失わ
れます。350ms から始めて、メッセージが途中から届くようなら上げてください。

| 設定 | 何のためのものか |
| --- | --- |
| **チャットを開く待ち時間** | チャット欄を開いてから入力するまでの待ち時間。メッセージが途中から届くときに上げるのはこれ |
| **チャットを開くキー** | チャット欄を開くもの。たいていのシムでは Enter |
| **送信キー** | 送信するもの。ふつうはこれも Enter |
| **キャンセルキー** | 送らずに欄を閉じるもの。待機中のメッセージを消すのに使う |
| **キーの保持時間** | 各キーを押している長さ。ゲームは 1 フレームに 1 回入力を読むので、1 フレームより短い押下はゲームが見ない押下になる |
| **入力の間隔** | 文字と文字のあいだの間隔 |
| **最大文字数** | これより長いメッセージは切られる。たいていのシムには独自の上限がある |
| **自動送信** | 送る前に確かめるなら切る — 上を参照 |
| **セッションプラグイン** | 誰がセッションにいるかを読み、名前が正しく文字になり、メンションになるようにする。*自動* のままで構わない |

### Unicode かスキャンコードか

**入力モード** は、文字がどうやってゲームに届くかを決めます。*unicode* は文字その
ものを送り、どんなキーボード配列にも、どんな文字体系にも対応します。ハードウェア
のスキャンコードを読むために、これを無視するゲームもあります。その場合は
*scancode* に切り替えてください。物理的にキーが押されたかのように入力します。

スキャンコードは US キーボードで打てるものに限られるので、アクセント付きの文字や
ラテン文字以外の文字体系は残りません。まず unicode を試してください。この設定があ
るのは、「ゲームが入力を無視する」への対処を、コードの変更ではなく設定の変更にす
る必要があったからです。

この二つはタイミングも別で、それがモードを分けている理由です。スキャンコードのキ
ーは `key_hold_ms` のあいだ保持されます。ゲームが 1 フレームに 1 回入力を読むから
です。文字の入力はそうしません — メッセージキューを通るので、1 文字 40ms では
200 文字のメッセージに 8 秒かかってしまいます。

## 名前と単語

音声モデルは聞こえたとおりに文字にしますが、ドライバー名はまさにそれが最も苦手と
するものです。セッションプラグインがセッションにいる人を読み取って名前を渡すので、
「Estre」は「Ester」ではなく「Estre」として出てきます。

**単語** はその上に自分の言葉を足すものです。スポンサー名、チーム名、友人のハンド
ルの実際の綴り。自分で直してばかりいるものは、追加する価値があります。

## 何も入力されない

**まずステータスタブを見てください。** フックが今どのキーで待機しているか、そして
トリガーが最後に見られたのがいつかが出ています。*最後のトリガー* が更新されないな
ら、問題は文字起こしではなくトリガーかフックです。

**管理者として実行する必要があります。** Windows は、送り主より高い整合性レベルで
動くプロセスへ送られた入力を捨てますし、シムはしばしば昇格して動いています。イン
ストール版は自動でこれを要求します。

**プロファイルが合っているか確認してください。** ステータスタブにはフォーカスされ
ている実行ファイル名が記録されます。それがどのプロファイルにも無いなら既定のプロ
ファイルが使われており、そのチャットキーはそのゲームに合っていないかもしれません。

**チャットを開く待ち時間を確認してください。** 冒頭の文字が欠けて届くのは、毎回か
ならず `pre_delay_ms` が短すぎるせいです。

**ゲームが unicode を無視していないか確認してください。** チャット欄は開くのに何も
現れないなら、入力モードを *scancode* にしてみてください。
